# The WebAssembly TCG backend (`tcg/wasm`)

xemu's Emscripten build no longer needs TCI. On `wasm32` hosts, `meson.build`
selects `tcg/wasm`, a native TCG backend that turns each translation block
(TB) into a small WebAssembly module. The JavaScript engine compiles that
module to machine code, so guest code runs as compiled code, not as
interpreted bytecode. TCI is still available with `--enable-tcg-interpreter`.

The backend targets the tree as of xemu v0.8.136 (QEMU 10.2.0) and the
toolchain in `tests/docker/dockerfiles/emsdk-wasm32-cross.docker`
(emsdk 3.1.50). It needs no newer emsdk and no wasm64 or Memory64 support.

## Files

| File | Purpose |
| --- | --- |
| `tcg/wasm/tcg-target.c.inc` | Code generator: TCG ops to WebAssembly bytecode, module framing. |
| `tcg/wasm/tcg-target*.h`, `tcg-target-con-*.h` | Usual per-backend headers (registers, supported ops, constraints). |
| `tcg/wasm/wasm-runtime.h` | Layout shared by generated code and the runtime (TB header, frame). |
| `tcg/wasm.c` | Runtime: instantiates modules through JavaScript, runs and chains TBs. |

Changes to generic code are small:

- `tcg/tcg.c` calls two new backend hooks, `tcg_out_set_label()` and
  `tcg_out_tb_end()`, when the backend defines
  `TCG_TARGET_STRUCTURED_CONTROL`. WebAssembly only has structured control
  flow, so the backend must know where labels are placed and must close its
  blocks once the TB is complete.
- `include/accel/tcg/getpc.h` gets a `CONFIG_TCG_WASM` branch for `GETPC()`.
  WebAssembly cannot read its own return address.
- `meson.build` picks `tcg_arch = 'wasm'` on `wasm32` and defines
  `CONFIG_TCG_WASM`. `tcg/meson.build` adds `tcg/wasm.c`.
- `tcg/region.c` no longer tries the memfd split-wx mapping on Emscripten.
  Emscripten's `mmap` of a file copies it, so the "executable" view never
  saw the generated code. `--enable-debug` builds turn split-wx on by
  default, which is how this showed up.

The backend leaves xemu's x87 FPU ops (`TCG_TARGET_HAS_fpu`) unimplemented,
so the i386 front end keeps using softfloat helpers, as it does on TCI.

## Execution model

WebAssembly code cannot jump into bytes it has just written to memory. The
generated bytes have to become a function first:

1. The code generator writes a complete module into the TCG code buffer at
   `tb->tc.ptr`, after a small `TCGWasmTBHeader`.
2. The first time the TB runs on a thread, `tcg_wasm_tb_exec()` (in
   `tcg/wasm.c`) passes the bytes to JavaScript. JavaScript runs
   `new WebAssembly.Module` and `new WebAssembly.Instance` against the main
   module's memory and function table, then adds the exported function to the
   table with `addFunction`.
3. The table index is cached in the TB header. After that, running the TB is
   an ordinary indirect call from C, with no JavaScript involved.

`tcg_qemu_tb_exec` points at `tcg_wasm_tb_exec`. The epilogue is a 4-byte
marker in the code buffer, used only as the "return to the main loop" value
for `goto_ptr`.

Each TB function has the signature `(i32 env, i32 frame) -> i32` and returns
the usual `exit_tb` value. `goto_tb` and `goto_ptr` return
`TCG_WASM_EXIT_CHAIN` instead, with the next TB's code pointer stored in the
frame, and `tcg_wasm_tb_exec` loops. Chaining goes through
`tb->jmp_target_addr[]` (the indirect jump method), so
`tb_target_set_jmp_target()` has nothing to patch.

### Registers and the frame

- TCG registers `r0`–`r29` are `i64` locals of the TB function. Locals cannot
  be clobbered by helpers, so only `r0` (the return value) is call-clobbered.
  The JavaScript engine allocates these locals to host registers.
- `TCG_AREG0` (env) and `TCG_REG_CALL_STACK` are the two `i32` parameters.
  The latter points at a `TCGWasmFrame` on the C stack of
  `tcg_wasm_tb_exec`. The frame holds the helper argument area, the TCG spill
  area, the current helper return address, and the Asyncify save area
  described below.
- `TCG_TARGET_REG_BITS` is 64 (WebAssembly has native `i64`), so 64-bit guest
  values never need register pairs. Pointers stay 32 bits.

### Control flow

TCG labels split the function body into segments, wrapped in a
`loop` + `br_table` dispatcher:

```
loop $dispatch
  block ... block           ;; one block per later segment
    local.get $seg
    br_table ...            ;; jump to segment $seg
  end
  segment 0
  end
  segment 1
  ...
end
```

A branch to a later segment is a single `br` or `br_if` out of the enclosing
blocks. A branch to an earlier segment (a loop in the TB) sets `$seg` and
branches back to the dispatcher. TBs without labels or calls get no
dispatcher at all.

### Helper calls

Arguments are stored by the generic code into the frame. The backend loads
them back onto the WebAssembly operand stack using the types from the
helper's `typemask`, then does `call_indirect` through the shared function
table, with the helper's address as the table index. Before each call, the
generated code stores the code address after the call into `frame.ra`.
`GETPC()` reads it through `tcg_wasm_ra_ptr`, so exception unwinding
(`cpu_restore_state`) maps the address back to the guest instruction as on
any native host.

`__int128` arguments are passed as two `i64` values, and `__int128` results
come back through a hidden pointer. This matches the wasm32 C ABI.

### Guest memory access

`qemu_ld` and `qemu_st` do the soft-TLB lookup inline:

1. Load the `CPUTLBDescFast` mask and table pointer for the MMU index from
   their fixed offsets before `env`.
2. Find the TLB entry and compare its tag with the page (and alignment bits)
   of the address.
3. On a hit, add `addend` and do a direct `i64.load*` or `i64.store*` on
   linear memory.

On a miss, execution falls into a separate segment that calls the
`helper_ld*_mmu` or `helper_st*_mmu` function. Guest RAM accesses that hit
in the TLB never leave the generated function.

### Asyncify and coroutines

QEMU on Emscripten implements coroutines with Asyncify
(`util/coroutine-wasm.c`). A helper such as an MMIO write that starts block
I/O can switch coroutines, which unwinds the whole C stack through the TB
function. Asyncify instruments the main module at link time. It cannot
instrument modules generated at run time, so the TB function cooperates:

- Each helper call that may have side effects, and each `qemu_ld`/`qemu_st`
  slow path, starts its own segment.
- After such a call returns, the generated code calls the imported
  `Asyncify.state` getter. If an unwind is in progress, it stores its live
  register locals and the segment number in the frame and returns.
- During the rewind, Asyncify re-enters `tcg_wasm_tb_exec` (which is
  instrumented) and calls the TB function again with the same frame. The
  function sees `frame.resume`, restores its locals, and jumps straight back
  to the call's segment. The helper is called again, continues its own
  rewind, and returns normally.

Helpers marked `TCG_CALL_NO_SIDE_EFFECTS` skip the check.

### Multiple threads and code-buffer flushes

Emscripten gives every pthread (Web Worker) its own function table, so a
table index is only valid on the thread that created it.
`TCGWasmTBHeader.owner` records which thread owns `TCGWasmTBHeader.func`.
Other threads instantiate their own copy and keep it in a per-thread hash
table. When `tb_flush()` resets the code buffer (`tb_ctx.tb_flush_count`
changes), each thread removes all of its functions from its table on its next
TB execution.

`MAX_CODE_GEN_BUFFER_SIZE` is 128 MiB. That bounds how many TB instances can
be live between flushes.

## Building

```sh
# Inside the emsdk-wasm32-cross container (tests/docker/dockerfiles/)
mkdir build && cd build
emconfigure ../configure --disable-docs --static --disable-tools \
    --target-list=i386-softmmu
emmake make -j$(nproc)
```

The summary prints `TCG backend: native (WebAssembly module per TB)`. Add
`--enable-tcg-interpreter` to get TCI again, for comparison.

A full xemu WebAssembly build is still blocked by the desktop OpenGL UI and
renderer (`epoxy` is required). See [README.md](README.md).

## Validation

Since xemu itself cannot link for the web yet, the backend was tested on an
upstream QEMU 10.2.0 tree with the same changes. xemu's `tcg/tcg.c`,
`tcg/region.c` and `tcg/wasm.c` were also compiled with `-DXBOX` against
the backend, with no warnings. Both trees were built with `--enable-debug`
(TCG assertions on) and emsdk 3.1.50, and `qemu-system-i386` was run under
Node.js 24, against a TCI build of the same tree:

| Workload | `tcg/wasm` | TCI | Result |
| --- | --- | --- | --- |
| SeaBIOS to "No bootable device" | 1.6 s | 3.3 s | identical serial output |
| `tests/tcg/multiarch/system/hello` | 1.6 s | 3.2 s | pass |
| `tests/tcg/multiarch/system/interrupt` | 1.4 s | 3.3 s | pass |
| `tests/tcg/multiarch/system/memory` (with unaligned checks) | 2.9 s | 35.2 s | pass, identical output |
| Boot sector doing 64 × 32-sector INT 13h reads from an IDE disk, then a checksum | 2.9 s | 5.7 s | correct checksum |

The short boots are dominated by start-up and first-run compile time. The
memory test, which reruns the same code, shows the steady-state gap (about
12×). In the disk test, more than 2,000 Asyncify unwinds passed through
generated TB code and were resumed correctly.

## Limitations and next steps

- **One module per TB.** Every TB pays a synchronous compile on first run and
  costs one instance. The next steps from [cpu-realtime.md](cpu-realtime.md)
  §2.2 still apply: compile hot regions with several TBs per module,
  compile in a background worker, and run cold code on TCI or the baseline
  tier first.
- **Chaining returns to C.** `goto_tb` returns to `tcg_wasm_tb_exec` instead
  of jumping directly. Region compilation, or `return_call_indirect` once the
  toolchain enables tail calls, would remove that round trip.
- **Asyncify check cost.** Each side-effecting helper call costs one extra
  call to the imported `Asyncify.state` getter.
- **Single-threaded TCG assumed.** `mb` emits nothing and memory ops are
  plain loads and stores. That is correct for xemu (one vCPU, no MTTCG). Real
  multi-vCPU support would need WebAssembly atomics.
- **Not implemented, so TCG expands them generically:** `extract2`,
  `divs2`/`divu2`, 64-bit `mulu2`/`muls2`/`muluh`/`mulsh`, 128-bit guest
  memory ops, 64-bit guest addresses, and xemu's native x87 FPU ops. WebAssembly
  `f64` would be a good fit for the FPU ops later.
